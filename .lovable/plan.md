# Бэкенд на бою актуален — переходим к причине падений

## Что подтвердил ваш вывод

- `af1ba06` = последний коммит репозитория, `register_shutdown_function` (строка 68) и `DEFAULT_ROWS = 500` (строка 133) на месте, кэши пересобраны.
- Значит, старые фаталы в логе (без `peak_mb`/`uri`) — это следы до деплоя. Все новые фаталы теперь будут писаться строкой `fatal_request` с URI, пользователем, `peak_mb` и текущим `memory_limit`.

Остаётся два несинхронизированных куска: **PHP memory_limit = 64M** и **старая сборка фронта** (лог 10:52 всё ещё просил колонку `body` у `notifications`, в репозитории такого запроса больше нет).

## Шаг 1. Поднять memory_limit до 256M (главное)

64M — аномально мало для Laravel: воркер умирает посреди запроса и **не возвращает MySQL-соединение**, соединения копятся до `max_user_connections`, фронт ретраит — лавина 500-х. Это связывает обе ошибки в одну.

В корне сайта (`/home/gro7659365/growth-peak.pro/docs`) создать/дополнить `.user.ini`:
```
memory_limit = 256M
```
Проверка (значение должно быть 256M, не 64M):
```
curl -s https://growth-peak.pro/api/health
php -r 'echo ini_get("memory_limit"),PHP_EOL;'
```
Если хостинг игнорирует `.user.ini` — тот же параметр через панель хостинга (PHP settings) или `php_value memory_limit 256M` в `.htaccess`.

## Шаг 2. Выложить свежий фронт

Запустить workflow `deploy-frontend.yml` (или собрать локально и залить `dist`), затем убедиться, что в `docs/index.html` подключён новый `assets/index-*.js`, и открыть сайт с Ctrl+Shift+R. Пока в браузере старый бандл, часть 500-х будет воспроизводиться из-за устаревших запросов.

## Шаг 3. Снять свежий срез ошибок

После шагов 1–2 попросить у вас:
```
grep -c "fatal_request" storage/logs/laravel.log
grep "fatal_request" storage/logs/laravel.log | tail -20
grep "1203" storage/logs/laravel.log | tail -5
```
Теперь у каждого фатала будет видно **точный URI и пиковую память** — дальше чиню адресно, а не по гипотезам.

## Шаг 4. Подтверждённые баги, чиню параллельно

- `EmailDomainPositionMapping` (модель, строки 9–15) не имеет связи `positions`, а `HRDDashboard.tsx` её запрашивает → гарантированный 500 на дэшборде HRD. Добавляю `position()`/`positions()`.
- `DbController::applySelect` при неизвестной связи падает в 500 — научу отдавать 400 с внятным текстом, чтобы такие рассинхроны фронта и моделей больше не роняли сервис.
- Аналитика (`src/lib/analytics/tracker.ts`) уже умеет замолкать при открытом circuit breaker; после шага 3 проверю по логу, остаётся ли `/api/analytics/ingest` источником коннект-шторма, и при необходимости добавлю серверный троттлинг с ответом 204 без обращения к БД.

Авторизованный прогон Playwright под HRD: логин → дэшборд → чаты → уведомления. Фиксирую коды ответов и наличие/отсутствие `fatal_request` в логе за время прогона. Закрываю задачу только по факту 200 на реальных данных.
