# /api/chats: почему сломалось и что делать дальше

## Что я проверил сейчас
- `https://growth-peak.pro/api/health` → 200 JSON, БД отвечает.
- `https://growth-peak.pro/api/chats` без токена → корректный 401 JSON (значит, роутинг и автозагрузчик в порядке; 500 возникает уже под авторизованным пользователем, на реальных данных).
- Код `ChatController::index` в репозитории: лимит 100 диалогов, окно 500 последних сообщений, один GROUP BY для непрочитанных.

Я пока НЕ подтвердил, какая именно строка падает на бою — для этого нужен текст ошибки из `storage/logs/laravel.log`. Всё, что ниже, — гипотезы, ранжированные по вероятности, и первый шаг плана как раз их отсекает.

## Почему «раньше такого не было»
Раньше на этом сервере чатов почти не существовало: в компании было несколько сотрудников и десятки сообщений. Затем мы засеяли боевую базу — 150 пользователей, ~1000 задач и ~1500 сообщений с комментариями. Старая реализация списка чатов грузила в PHP всю историю сообщений всех диалогов и делала отдельный COUNT на каждый диалог. При 64 МБ `memory_limit` на хостинге это перестало помещаться в память — endpoint начал падать в 500 и заодно съедать лимит MySQL-соединений. То есть код не «сломался» — он перестал влезать в ресурсы, когда данных стало в сотни раз больше.

Второй фактор: боевой бэкенд не всегда совпадает с репозиторием. Один деплой уже оставил битый `vendor/composer`, а версия MySQL на shared-хостинге не приняла вариант с `joinSub`. Поэтому «исправлено в коде» ≠ «исправлено на сервере», пока мы не увидим лог.

## План

### Шаг 1. Получить точную ошибку (без него дальше не идём)
На сервере:
```
cd /home/gro7659365/growth-peak.pro/docs/backend
grep -n "chats" -A 30 storage/logs/laravel.log | tail -n 120
```
Нужны: класс исключения, сообщение, файл и строка. Это сразу разделяет три сценария:
- `Allowed memory size ... exhausted` → упираемся в 64 МБ;
- `SQLSTATE[...]` → несовместимый SQL или отсутствующая колонка/индекс;
- `max_user_connections` → шторм соединений, а не сам чат.

### Шаг 2. Убедиться, что на бою именно текущий код
Сверяем, что в задеплоенном `ChatController.php` есть `limit(100)` и нет `joinSub`, и что кэши сброшены (`php artisan optimize:clear`). Если файл старый — проблема в деплое, а не в логике.

### Шаг 3. Исправление по результату шага 1
- Память: убрать hydration моделей в `index` (перейти на `DB::table` + выборку только нужных колонок), отдавать диалоги страницами по 30.
- SQL: заменить проблемную конструкцию на простые запросы, совместимые с MySQL 5.7.
- Соединения: закрывать соединение перед долгими операциями и убедиться, что 503 отдаётся вместо 500, чтобы срабатывал circuit breaker на клиенте.

### Шаг 4. Проверка на бою
Авторизованный прогон `/api/chats` через Playwright под реальной учёткой, замер времени ответа и peak memory из лога. Считаю задачу закрытой только после 200 с реальными данными.

### Шаг 5. Убрать корневое ограничение
`memory_limit = 64M` — аномально мало для Laravel. Поднять до 256M через `.user.ini` или панель хостинга. Без этого любой рост данных снова выстрелит в другом модуле (аналитика, уведомления, оргструктура).
