# Performance: детализация циклов, наполнение демо-данными и ускорение прогноза

## 1. Провалиться в цикл оценки

Сейчас на вкладке «Циклы» карточка цикла показывает только название, период и кнопки открыть/закрыть — детального экрана нет.

Добавим страницу цикла `/performance/cycles/:id`:
- Шапка: название, период, дедлайн, статус, веса (self/manager/peer).
- Сводка: сколько ревью создано, сколько в каждом статусе (draft / self_done / manager_done / finalized), средний итоговый балл, прогресс-бар завершённости.
- Таблица участников: сотрудник, должность, отдел, руководитель, статус, self/manager/peer/final баллы, дата финализации. Поиск, фильтр по статусу и отделу, сортировка по итоговому баллу.
- Клик по строке — раскрытие деталей ревью: фидбек по ролям (сильные стороны, зоны роста, комментарии, оценки по компетенциям), список приглашённых ревьюеров 360° и их статусы.
- Кнопки открыть/закрыть цикл переносятся и на страницу цикла; карточки в списке становятся кликабельными.
- Мобильная версия: карточки вместо таблицы (как в остальных модулях).

Бэкенд: новый эндпоинт `GET /api/performance-cycles/{id}/detail` — один агрегированный raw-SQL запрос (reviews + profiles + feedback counts), чтобы не тянуть Eloquent-гидрацию.

## 2. Наполнение демо-данными всего блока Performance

Расширяем `SeedDemoCompany` (и добавляем возможность досеять только этот блок, как сделано для карьерных треков):

- **Циклы оценки**: 3 цикла — закрытый (прошлый год), закрытый (H1), открытый текущий. У закрытых — все ревью финализированы с реальными self/manager/peer/final баллами и текстовым резюме.
- **Ревью и фидбек**: для каждого сотрудника записи `performance_reviews` + `performance_review_feedback` от self, руководителя и 2–3 коллег, с оценками по компетенциям, сильными сторонами и зонами роста (осмысленные тексты под должность, не «lorem»).
- **Ревьюеры 360°**: заполненные `performance_review_reviewers` со статусами invited/submitted/declined.
- **Испытательные сроки**: ~12–15 сотрудников с недавним hire_date — активные (с разной степенью прохождения чек-листа), пройденные, продлённые и один непройденный; у каждого 4–6 критериев с частичной отметкой выполнения и целями.
- **Дисциплинарные записи и PIP**: несколько предупреждений разной серьёзности, активный PIP с критериями, закрытая запись, наблюдение.
- **Встречи 1:1**: прошедшие встречи с повесткой и заметками + пара запланированных.
- **Talent Review / 9-box** и ассессменты — дозаполняем, чтобы матрица и «Мои оценки» не были пустыми.

Распределение баллов делаем правдоподобным (нормальное вокруг 3.4–4.0), чтобы аналитика и 9-box выглядели живыми. Сидер идемпотентный: повторный запуск не дублирует записи.

## 3. Прогноз: долгая загрузка и нулевые значения

Подтверждено по коду: в `AttritionPredictionService::recomputeCompany` запись результатов идёт по одной строке — на каждого сотрудника отдельный SELECT + отдельный UPDATE/INSERT. На 150+ сотрудниках это сотни запросов в одном HTTP-вызове, отсюда долгий ответ и таймауты.

Что делаем:
- Заменяем построчный цикл на пакетный `upsert` по ключу (`user_id`, `horizon_days`) чанками по 200 строк в одной транзакции.
- Возвращаем в ответе `updated`, `avg_probability` и `bands`, чтобы UI мог обновиться сразу, не дожидаясь повторных запросов.
- Причина нулей отдельно диагностируется на боевой БД: проверяем, есть ли строки в `attrition_predictions` после пересчёта и совпадает ли в них `company_id` с компанией пользователя (upsert ищет строку только по `user_id`+`horizon_days`, из-за чего строка, созданная под другой компанией, могла остаться с чужим `company_id`, а `overview` фильтрует по `company_id`). Если диагностика подтвердит это — добавляем `company_id` в ключ сопоставления и чиним привязку существующих строк.
- Если после пересчёта сигналов действительно нет (пустые задачи/1:1/признания в демо), вероятности будут одинаково низкими — п.2 (наполнение данными) закрывает и это.
- В UI: кнопка «Пересчитать прогноз» показывает прогресс и тост с числом обновлённых записей; после успеха данные перечитываются принудительно (`refetch`, а не только инвалидация).

## 4. Мелочи из консоли

- `POST /api/analytics/ingest` c `ERR_HTTP2_PING_FAILED` — ответ 202 приходит, но соединение рвётся. Переводим отправку батча аналитики на `navigator.sendBeacon` с фолбэком на `fetch(..., { keepalive: true })` и глушим сетевые ошибки трекера, чтобы они не шумели в консоли.
- Форс-рефлоу и долгий `setTimeout` — уменьшаем за счёт виртуализации/пагинации длинных таблиц на новой странице цикла (рендер порциями по 50 строк).
