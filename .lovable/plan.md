# Устранение корня `max_user_connections`

## Подтверждённая цепочка

Лог показывает, что MySQL отклоняет подключение уже на первом запросе Sanctum к `personal_access_tokens`. Значит, запрос токена не является причиной: к этому моменту лимит соединений уже исчерпан.

В коде подтверждён механизм самоподдерживающейся перегрузки:

- REST-клиент повторяет проблемный GET до 3 раз;
- глобальный TanStack Query работает с дефолтным `retry: 3`, поэтому каждая неудачная query запускает весь цикл REST-клиента повторно — до 12 HTTP-запросов на один логический GET;
- при восстановлении сети и возврате фокуса одновременно перезапускаются все активные query;
- глобальный опрос чатов идёт каждые 7 секунд, сообщения открытого чата — каждые 5 секунд;
- продуктовая аналитика отправляется отдельным `fetch`, обходит общий ограничитель и при API-ошибках создаёт дополнительный трафик;
- тяжёлые экраны запускают несколько независимых запросов одновременно.

Это объясняет положительную обратную связь: нехватка соединений вызывает ретраи, ретраи увеличивают число PHP-запросов и новых попыток подключения, после чего база не успевает выйти из перегрузки.

## 1. Снять серверный снимок владельцев соединений

До изменения кода зафиксировать в момент инцидента:

- `SHOW FULL PROCESSLIST` и количество соединений пользователя БД по `COMMAND`/`STATE`;
- значения `max_user_connections`, `max_connections`, `Threads_connected`, `Threads_running` и `wait_timeout`;
- количество PHP-FPM процессов, artisan workers, scheduler и Reverb-процессов;
- частоту запросов по маршрутам из access-log за минуту.

Это определит вторую половину корня: соединения создаёт преимущественно HTTP-лавина либо их постоянно держит ошибочно запущенный долгоживущий процесс. Если у пользователя БД нет права на полный processlist, собрать доступную часть и запросить у хостера число активных соединений по этому DB user.

## 2. Разорвать каскад ретраев на фронте

- Настроить глобальный `QueryClient`: не повторять `4xx`; для сетевых ошибок/`5xx` оставить не более одной контролируемой попытки; отключить массовый refetch при фокусе и reconnect во время перегрузки; задать разумный `staleTime`.
- Оставить единственный уровень повторов: транспортный клиент отвечает за короткий backoff на `503 db_busy`, TanStack Query повторно не умножает этот цикл.
- Добавить общий circuit breaker: после серии `db_busy` временно не запускать новые фоновые/refetch-запросы, но разрешать явное действие пользователя «Повторить».
- Таймаут сети не должен сбрасывать валидную сессию: текст и поведение разделить для реального `401/419` и временной недоступности backend.

## 3. Убрать постоянную фоновую нагрузку

- Приостановить опрос списка чатов при скрытой вкладке и увеличить интервал; сообщения опрашивать только при открытом чате.
- Убрать лишний `markRead`, если после последнего чтения новых сообщений нет.
- Перевести analytics ingest под единый лимит/circuit breaker либо полностью отключать ingest на период `db_busy`; события ошибок перегрузки не должны порождать новый запрос к той же перегруженной базе.
- Проверить самые тяжёлые стартовые экраны и объединить связанные bootstrap-запросы или запускать второстепенные данные после критичных.

## 4. Ограничить серверную конкуренцию ниже лимита MySQL

По результату processlist:

- согласовать `pm.max_children` PHP-FPM с фактическим `max_user_connections`, оставив резерв для CLI/миграций;
- убрать дублирующиеся queue/Reverb/scheduler процессы; при `QUEUE_CONNECTION=sync` не держать ненужные queue workers;
- убедиться, что PDO persistent connections не включены;
- для долгоживущих artisan/Reverb-процессов явно освобождать DB-соединение после работы и перезапускать их с лимитами времени/заданий;
- увеличить лимит у хостера только после устранения умножения запросов — это резерв ёмкости, а не основной фикс.

## 5. Проверка на production-профиле

- Выполнить вход и пройти HRD/employee/tracker сценарии с записью Network и access-log.
- Проверить число HTTP-запросов при первом открытии, при `503`, возврате фокуса и восстановлении сети.
- Критерии: один логический GET не создаёт каскад; фоновые запросы прекращаются при `db_busy`; число соединений возвращается к базовому после всплеска; пользователь видит временную недоступность без разлогина и чёрного экрана.

## Технические точки изменения

- `src/App.tsx` — глобальная политика TanStack Query.
- `src/integrations/laravel/client.ts` — единый retry/circuit breaker и корректная классификация таймаута.
- `src/contexts/ChatContext.tsx`, `src/components/chat/ConversationView.tsx` — управляемый polling.
- `src/lib/analytics/tracker.ts` — отключение обратной связи при перегрузке.
- конфигурация PHP-FPM/Supervisor на сервере — только после фактического снимка процессов и лимитов.
