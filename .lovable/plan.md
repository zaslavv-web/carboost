## Цель
Снять повторяющийся 500 при `POST /api/performance-cycles/{id}/open` не точечно, а по всей цепочке: открыть цикл, создать reviews, отправить уведомления и показать понятную ошибку в UI.

## Что проверено по коду
- Роут существует: `POST /api/performance-cycles/{id}/open` ведёт в `PerformanceController::openCycle`.
- `profiles` действительно не содержит `is_active`, значит старый фикс был нужен, но он не исчерпал проблему.
- В текущем коде остаются зоны риска schema drift: реальные prod-таблицы могут отличаться по `performance_reviews`, `performance_cycles`, `team_members`, `notifications`.
- Фронт сейчас показывает только общий `error.message`; если backend отдаёт 500 без JSON-деталей, HR видит бесполезный “server error”.

## План исправления

### 1. Добавить безопасную диагностику в `openCycle`
В `PerformanceController::openCycle()` обернуть каждый этап в явный диагностический блок:
1. проверка прав HR;
2. поиск цикла;
3. проверка обязательных колонок таблиц;
4. обновление статуса цикла;
5. выборка сотрудников компании;
6. создание/пропуск review по каждому сотруднику;
7. отправка уведомлений.

При ошибке endpoint должен возвращать JSON вида:
```json
{
  "ok": false,
  "step": "create_review",
  "message": "...",
  "diagnostics": {
    "cycle_id": "...",
    "company_id": "...",
    "required_columns": { ... },
    "created": 0,
    "existing": 0,
    "errors": []
  }
}
```
Это сразу покажет реальную причину вместо слепого 500.

### 2. Сделать `openCycle` устойчивым к различиям схемы
Внести защиту от всех вероятных runtime-причин:
- не использовать Eloquent `update()`/`firstOrCreate()` там, где timestamps/модельные события могут падать;
- вставлять только те колонки, которые реально существуют в `performance_reviews`;
- проверять наличие `company_id`, `manager_id`, `created_at`, `updated_at` перед записью;
- если `notifications` имеет старую схему (`message/type`) или новую (`description/notification_type`) — писать в существующие колонки;
- если уведомление не удалось — не ронять открытие цикла, а вернуть это в `notification_errors`.

### 3. Защитить создание цикла
Проверить и исправить `storeCycle()`:
- если HRD/company_admin создаёт цикл — `company_id` должен гарантированно ставиться из пользователя;
- если superadmin без активной компании создаёт цикл — вернуть понятную 422 ошибку, а не создавать “бесхозный” цикл;
- при отсутствии нужных колонок вернуть диагностический JSON.

### 4. Улучшить фронтовую ошибку
В `src/pages/Performance.tsx`:
- после `openCycle` показывать не только `Server Error`, а `step/message` из backend JSON;
- при частичном успехе показывать: сколько reviews создано, сколько уже было, сколько уведомлений не ушло;
- после успешного открытия инвалидировать `cycles`, `reviews mine/team/all`.

### 5. Добавить read-only preflight endpoint для HRD/superadmin
Добавить безопасный endpoint, например:
```text
GET /api/performance-cycles/{id}/open-preflight
```
Он ничего не меняет, а возвращает:
- найден ли цикл;
- `company_id` цикла;
- сколько сотрудников будет затронуто;
- какие обязательные таблицы/колонки есть или отсутствуют;
- есть ли уже reviews;
- какая схема у notifications.

Это позволит проверить прод без повторного “ломающего” POST.

### 6. Проверка после внедрения
- Локально: синтаксис PHP через доступный PHP/Nix.
- На проде после deploy: сначала `open-preflight`, затем `open` для проблемного цикла.
- Если prod всё ещё вернёт ошибку — ответ будет содержать `step`, и следующий фикс будет уже по точному месту, а не гипотезе.

## Ожидаемый результат
- Открытие цикла больше не падает из-за уведомлений, timestamp-колонок или старой схемы.
- Любая оставшаяся ошибка будет возвращаться как структурированный JSON с точным шагом.
- HRD увидит нормальное сообщение в интерфейсе, а не общий 500.
