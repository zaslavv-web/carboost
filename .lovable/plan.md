# Почему всё падает: боевой сервер работает на старом коде

## Что доказывает лог

1. **`max_user_connections` приходит из `/api/analytics/ingest`** (кадр #17: `AnalyticsController->ingest`, строка 51). Это фоновая телеметрия фронта: она бьёт по API десятками запросов и жрёт коннекты Sanctum-guard'а ещё до того, как пользователь что-то открыл.
2. **Fatal `Allowed memory size of 67108864 bytes exhausted` (userId 1259), 5 раз за 6 секунд**, `Connection.php:412`, стек `#0 {main}`.
3. **`Unknown column 'body' in 'field list'`** на `notifications` в 10:52.

## Ключевой вывод: на бою НЕ тот код, что в репозитории

Два независимых доказательства:

- В репозитории `AppServiceProvider.php:68` уже стоит `register_shutdown_function`, который при фатале логирует `peak_mb`, URI и query string. В вашем логе у фаталов этих полей нет — только голое `#0 {main}`. Значит, задеплоенный `AppServiceProvider` старее репозитория.
- В репозитории фронт больше нигде не запрашивает колонку `body` у `notifications` (проверил grep по `src/`). А боевой лог в 10:52 её всё ещё шлёт. Значит, в браузере/на сервере работает старая сборка фронта.

Отсюда и ощущение «не исправлено»: правки лежат в репозитории, но до `growth-peak.pro` не доехали (или доехали частично — вспомните оборванный `composer install` с битым автозагрузчиком).

## Почему «раньше такой проблемы не было»

Раньше база была почти пустой. После сидинга — 150 сотрудников, ~1000 задач, ~1500 сообщений. При `memory_limit = 64M` любой запрос без лимита теперь не влезает в память, PHP-воркер умирает **не отдав MySQL-соединение**, соединения копятся до `max_user_connections`, следующий запрос падает в 500, фронт ретраит — и получается лавина. Плюс аналитика-ingest подливает трафик. Код не «сломался» — он перестал помещаться в ресурсы хостинга.

### Шаг 1. Синхронизировать бой с репозиторием (это первично)

Плюс пересобрать и выложить фронт (проверить, что в `docs/assets` новый `index-*.js`, и обновить страницу с Ctrl+Shift+R). Пока обе стороны не совпадают с репо, любые новые правки диагностировать бессмысленно.

### Шаг 2. Поднять memory_limit
`64M` для Laravel аномально мало. `.user.ini` в корне сайта: `memory_limit = 256M`, проверить через `php -i | grep memory_limit` и страницу phpinfo. Это снимает первопричину «воркер умер, коннект завис».

### Шаг 3. Убрать аналитику как источник шторма
- `AnalyticsController::ingest`: батчить события и жёстко ограничить частоту; при нехватке коннектов — возвращать 204 без обращения к БД.
- На фронте (`src/lib/analytics/tracker.ts`, `AnalyticsBootstrap.tsx`): отправка пачкой раз в N секунд, отключение при скрытой вкладке, полное молчание при открытом circuit breaker.

### Шаг 4. Добить `/api/chats`
После шага 1 повторить запрос и посмотреть свежий фатал уже с `peak_mb` и URI (их теперь будет писать shutdown-хендлер). Если это память — перевести `ChatController::index` на `DB::table` без гидрации моделей и пагинацию по 30 диалогов.

### Шаг 5. Побочный подтверждённый баг
`EmailDomainPositionMapping` не имеет связи `positions`, а `HRDDashboard.tsx:308` её запрашивает → 500 на дэшборде HRD. Добавить relation и научить `DbController::applySelect` игнорировать неизвестные связи вместо 500.

### Шаг 6. Проверка
Авторизованный прогон через Playwright под HRD: логин, дэшборд, чаты, уведомления. Фиксирую коды ответов и `peak_mb` из лога. Закрываю только по факту 200 на реальных данных.
