# Устранить 500 на профилях и должностях с обязательным боевым E2E

## Подтверждённое состояние

- Боевой backend отвечает версией `096f235` и сообщает 9 фатальных ошибок за последний час; последний URI — `/api/db/positions?select=*&order=title.asc`.
- Запрос должностей в текущем коде не имеет статического списка колонок и поэтому вызывает `Schema::getColumnListing()` на горячем пути.
- HRD-экран напрямую вызывает оба падающих запроса: `/profiles?per_page=500&company_id=...` и generic `/db/positions?select=*`.
- `/profiles` уже использует raw SQL, но забирает до 501 профиля одной выборкой и затем отдельной выборкой все роли. По имеющимся данным нельзя честно утверждать, на какой именно стадии этот endpoint падает на бою.
- Автоматизированных регрессионных тестов для этих двух маршрутов сейчас нет.

## План исправления

### 1. Зафиксировать точную стадию падения `/api/profiles`

- Добавить безопасную стадийную диагностику endpoint: авторизация, определение компании, чтение профилей, чтение ролей, сериализация.
- Для каждого аварийного ответа писать `error_id`, стадию, число строк, PHP/Zend memory и число SQL-запросов без персональных данных.
- Получить боевой ответ и соответствующую запись лога под HRD-учёткой; только после этого фиксировать корневую причину профилей.

### 2. Убрать metadata-path у должностей

- Добавить `positions` в статическую карту разрешённых колонок generic DB bridge.
- Исключить `Schema::getColumnListing()` / `SHOW COLUMNS` для чтения должностей во всех экранах.
- Сохранить company scope и существующий формат ответа, чтобы не ломать потребителей.

### 3. Сделать каталог сотрудников ограниченным и устойчивым

- Перевести `/api/profiles` на порционное чтение профилей и ролей с жёстким пределом ответа; не материализовывать 500 строк и весь набор ролей одновременно.
- Использовать только компанию из серверного auth-контекста для HR/HRD/company admin; входной `company_id` оставить только superadmin.
- На HRD-экране запрашивать фактически нужные поля и нормальный размер страницы вместо `per_page=500`.
- Убрать повторные автоматические попытки именно для этих запросов: один отказ не должен превращаться в серию одинаковых 500.

### 4. Добавить регрессионные проверки до выкладки

- Backend feature-test: HRD компании с одним сотрудником получает `200` от `/api/profiles`, корректные email/roles и не видит чужую компанию.
- Backend feature-test: `/api/db/positions?select=*&order=title.asc` возвращает `200`, фильтруется по компании и не выполняет запросов к metadata (`SHOW COLUMNS`).
- Тест на верхнюю границу каталога и пагинацию, чтобы большой tenant не вернул проблему позже.
- Frontend test: HRD dashboard делает по одному запросу каталога и должностей и не запускает retry-loop на 500.

### 5. Боевой E2E — обязательный критерий готовности

- После выкладки войти реальной HRD-учёткой и открыть тот экран, где воспроизводится ошибка.
- Playwright должен зафиксировать `200` для `/api/profiles` и `/api/db/positions`, отсутствие повторных запросов и заполненный интерфейс.
- Сравнить `fatals_last_hour` до и после прогона: счётчик не должен увеличиться, а `fatals_last_uri` не должен обновиться тестовыми запросами.
- Проверить заголовок `X-App-Version`, чтобы доказать, что тестируется именно новый backend.
- Не сообщать «исправлено», пока авторизованный боевой прогон не пройден. Сейчас в среде нет активной боевой сессии или тестовых credentials; если их нельзя восстановить из разрешённого тестового контура, перед финальной проверкой потребуется повторно предоставить доступ безопасным способом.
