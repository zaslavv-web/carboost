# Разбор лога: что он показал и что делать

## Главное: в этом фрагменте лога нет ошибки `/api/chats`
`grep -n "chats"` совпал не с HTTP-запросом, а со старыми записями от **14 июля** про артисан-команду `chats:seed` (её не существует). Это шум от прошлого сеанса сидинга, к текущему 500 отношения не имеет. Значит, вопрос «что случилось с чатами» лог пока не закрывает — нужен свежий срез (см. шаг 1).

## Что лог всё-таки доказал: реальный 500 на дэшборде HRD
Строка 135:
```
Call to undefined relationship [positions] on model [App\Models\EmailDomainPositionMapping]
DbController.php(176) -> Builder->get()
```
Причина подтверждена чтением кода:
- `src/pages/HRDDashboard.tsx:308` запрашивает `select("id, email_domain, position_id, positions(title, department)")`;
- `DbController::applySelect` превращает `positions(...)` в `->with('positions')`;
- в `backend-laravel/app/Models/EmailDomainPositionMapping.php` (15 строк, только `$fillable`) никаких связей нет.

Итог: любой заход HRD на дэшборд роняет этот запрос в 500. Это как раз один из «почти все сервисы отвечают 500» — часть из них не про базу, а про такие рассинхроны фронта и моделей.

## Почему «раньше не было»
Два независимых накопительных фактора:
1. **Данные выросли.** Мы засеяли боевую базу (150 сотрудников, ~1000 задач, ~1500 сообщений). Код, который грузил всю историю чатов в PHP, перестал влезать в `memory_limit = 64M`. Раньше при десятке записей он «работал» только потому, что данных почти не было.
2. **Фронт ушёл вперёд моделей.** Запросы вида `positions(...)` писались под PostgREST-совместимость, а в Laravel-моделях соответствующих relation-методов не создали. Пока эти экраны не открывались на реальных данных/ролях — ошибка не проявлялась.

То есть система не «сломалась вчера» — она вышла из тепличного режима.

## План

### Шаг 1. Достать настоящую ошибку `/api/chats`
На сервере (фильтр по свежей дате, а не по слову "chats"):
```
cd /home/gro7659365/growth-peak.pro/docs/backend
tail -n 400 storage/logs/laravel.log | grep -n "2026-08-13" -A 25 | head -n 150
```
Нужны класс исключения, файл и строка. Без этого чинить чаты — гадание.

### Шаг 2. Исправить подтверждённый баг связей
- Добавить в `EmailDomainPositionMapping` relation `position()` и алиас `positions()` → `belongsTo(Position::class, 'position_id')`.
- Пройти по остальным моделям из `MODEL_MAP` и сверить с `select=...(...)`, которые реально шлёт фронт (`rg "\w+\(" src` по вызовам `.select(`), чтобы закрыть тот же класс ошибок разом, а не по одной.
- В `DbController::applySelect` — не падать в 500 на неизвестной связи: логировать и игнорировать её (данные вернутся без вложенного объекта), плюс отдавать 400 вместо 500.

### Шаг 3. Починить `/api/chats` по результату шага 1
Вероятные ветки: память (перейти на `DB::table` без hydrate моделей, пагинация по 30 диалогов), несовместимый SQL (упростить под MySQL 5.7), либо перегрузка соединений (503 вместо 500).

### Шаг 4. Проверка на бою
Авторизованный прогон через Playwright под учёткой HRD: дэшборд + чаты, фиксируем коды ответов и время. Считаю закрытым только по факту 200 на реальных данных.

### Шаг 5. Снять корневое ограничение
`memory_limit = 64M` — аномально мало. Поднять до 256M через `.user.ini` или панель хостинга; иначе следующий рост данных выстрелит в другом модуле.
