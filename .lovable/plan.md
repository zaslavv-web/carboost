# Надёжная доставка .htaccess при деплое фронта

## Проблема

Шаг «Применить .htaccess на сервере» падает с `.htaccess.cache не доехал на сервер`: он ищет файл `dist/.htaccess.cache`, который должен был приехать по rsync в веб-рут. Сейчас вся доставка правил веб-сервера зависит от того, что rsync довёз скрытый файл — и если этого не произошло (исключения, права, особенности хостинга), деплой обрывается, а старый `.htaccess` остаётся на сервере.

## Решение

Перестать зависеть от rsync для этого файла: передавать содержимое `.htaccess` прямо в SSH-сессию.

1. В шаге сборки продолжать формировать локальный файл (заголовок + `public/.htaccess`) — он остаётся единственным источником правил и виден в логах.
2. Шаг «Применить .htaccess на сервере» переписать так, чтобы содержимое файла передавалось на сервер через stdin SSH (base64, чтобы не ломались кавычки и переносы строк), декодировалось во временный файл, проверялось на непустоту и наличие `RewriteEngine`, и только после этого атомарно заменяло текущий `.htaccess` (с бэкапом `.htaccess.bak`).
3. Если приехавший по rsync `.htaccess.cache` всё же есть — удалять его, чтобы не копился мусор в веб-руте.
4. Добавить проверку после применения: вывести первые строки серверного `.htaccess` и сравнить его контрольную сумму с локальной; при расхождении — падать с понятной ошибкой.
5. Оставить `--exclude '.htaccess'` в rsync (чтобы rsync не трогал живой файл), но убрать зависимость деплоя от `.htaccess.cache`.

## Технические детали

Файл: `.github/workflows/deploy-frontend.yml`

- Шаг «Собрать .htaccess для сервера»: дополнительно посчитать `sha256sum` и положить его в `GITHUB_ENV` (`HTACCESS_SHA`).
- Шаг «Применить .htaccess на сервере»:
  ```
  B64="$(base64 -w0 dist/.htaccess.cache)"
  $SSH "$DEPLOY_USER@$DEPLOY_HOST" "WEB_ROOT='$WEB_ROOT' B64='$B64' EXPECT='$HTACCESS_SHA' bash -s" <<'REMOTE'
  set -e; cd "$WEB_ROOT"
  printf '%s' "$B64" | base64 -d > .htaccess.new
  test -s .htaccess.new
  grep -q 'RewriteEngine' .htaccess.new
  [ -f .htaccess ] && cp .htaccess .htaccess.bak
  mv .htaccess.new .htaccess
  rm -f .htaccess.cache
  sha256sum .htaccess
  REMOTE
  ```
  и сравнение полученной суммы с `EXPECT` (с фолбэком на `shasum`/`md5sum`, если `sha256sum` на хостинге нет).
- Ошибочное сообщение `.htaccess.cache не доехал на сервер` удаляется вместе с проверкой наличия файла.

После правки прогоняю деплой фронта и проверяю, что шаг проходит, `https://growth-peak.pro/` отдаёт 200, SPA-роуты не уходят в петлю редиректов, а `version.json` доступен напрямую.
