# Проверка после выкладки raw-SQL чатов

Деплой встал: `/api/health` → 200, `memory_limit` = 256M, кэши очищены. Единственный `api_fatal` в логе — от 15:35:59, то есть ДО этой выкладки. Значит новый код ещё ни разу не проверялся под реальной нагрузкой.

## Шаг 1. Воспроизвести сценарий
Открыть сайт в приватном окне (или Ctrl+Shift+R), войти под пользователем, у которого падало, зайти в раздел «Чаты», открыть 2-3 диалога.

## Шаг 2. Снять логи
```bash
cd /home/gro7659365/growth-peak.pro/docs/backend
grep -n "api_memory_high\|api_fatal\|chat.index" storage/logs/laravel.log | tail -20
```

## Что означает результат
- Пусто → падение устранено, переходим к следующей задаче.
- Есть `api_memory_high` → в строке будет точный URI и пик памяти: правим именно этот эндпоинт (следующие кандидаты — `/api/db/*` c большими `select` и дашборд HRD).
- Есть новый `api_fatal` с временем позже выкладки → в строке будет файл и строка падения; правим адресно.

## Технические детали
- `index()`, `unreadCount()`, `contacts()`, `messages()` в `ChatController` переведены на `DB::table` — Eloquent-гидрация и `CompanyScope` больше не участвуют в горячем пути.
- `MemoryWatchdog` стоит первым в `api`-группе и логирует любой запрос с пиком ≥96 МБ, включая успешные (200) — это даёт предупреждение до фатала.
- Порог 96 МБ при лимите 256 МБ выбран так, чтобы поймать рост задолго до обрыва.
