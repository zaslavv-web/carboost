# Починить проверку версии после деплоя фронта

## Что показала диагностика (проверено сейчас)

- Файлы фронта на боевом сервере **свежие**: `/assets/index-CWuHFszl.js` и `/manifest.json` имеют `Last-Modified` 24.08.2026 12:53 UTC — то есть rsync прошёл успешно, деплой доехал.
- `https://growth-peak.pro/version.json` отдаёт **не JSON, а `index.html`** (`content-type: text/html`, 2736 байт) — то есть по этому пути файл не отдаётся и срабатывает SPA-фолбэк на index.html.
- При этом другие статические JSON отдаются нормально (`/manifest.json` → `application/json`), значит правило перезаписи «глотает» не все `.json`, а именно отсутствующий файл.
- В логе воркфлоу строка была `version.json:` (пусто), сейчас же приходит HTML — ответ нестабилен, поэтому шаг проверки падает по двум разным причинам и не показывает, что реально пришло.

Итог: деплой рабочий, падает только пост-проверка. Точную причину отсутствия/недоступности `version.json` на сервере надо подтвердить прямо на хосте — это первый шаг плана.

## Что сделаем

1. **Подтвердить факт на сервере**: сразу после rsync по SSH проверять наличие и содержимое `version.json` в веб-руте (`ls -l` + `cat`). Если файла нет — значит он не доезжает и шаг падает с понятной ошибкой; если есть, а по HTTP отдаётся index.html — причина в правилах перезаписи/кэше, и это видно из лога.
2. **Сделать пост-проверку устойчивой**: повторять запрос несколько раз с паузами (сервер и кэш могут отставать), отправлять `Cache-Control: no-cache` и уникальный query-параметр, печатать HTTP-код, content-type и первые строки тела. Различать три случая: пустой ответ (сеть/таймаут), HTML вместо JSON (файл не отдаётся), JSON с другой версией (реально старый файл).
3. **Не валить деплой из-за проверки, если файлы уже доехали**: если SSH-проверка подтвердила правильную версию в веб-руте, а HTTP отдаёт фолбэк — писать `::warning::` вместо `exit 1`, чтобы зелёный деплой не блокировался косметикой. Реальное расхождение версий по-прежнему валит шаг.
4. **Исключить SPA-фолбэк для служебных файлов**: добавить в управляемый блок `.htaccess` правило, чтобы существующие файлы (`version.json`, `manifest.json`, `robots.txt`) отдавались напрямую и не переписывались на `index.html`.

## Технические детали

- Файл: `.github/workflows/deploy-frontend.yml`.
  - Новый шаг после `Deploy (rsync…)`: SSH-команда `ls -l "$WEB_ROOT/version.json" && cat "$WEB_ROOT/version.json"`, результат в `$GITHUB_ENV` как `SERVER_VERSION_OK=true|false`.
  - Шаг `Post-deploy check`: цикл до 5 попыток с `sleep 5`, `curl -s -w '%{http_code} %{content_type}'`, отдельные ветки для пустого тела / `text/html` / несовпадения SHA; при `SERVER_VERSION_OK=true` и HTML-фолбэке — предупреждение, а не падение.
  - Управляемый блок `.htaccess` (генерируется в шаге `Cache headers`) дополняется `RewriteCond %{REQUEST_FILENAME} -f` + `RewriteRule ^ - [L]` перед SPA-правилом, чтобы существующие файлы не уходили в `index.html`.
- Изменения только в воркфлоу и в генерируемом блоке `.htaccess`; код приложения и бэкенд не трогаем.
