# /api/chats: найти и убрать источник 250 МБ

## Что показал лог (факт)

Строка `api_fatal` от 13.08 15:35:59: `/api/chats`, `Allowed memory size of 268435456 bytes exhausted`, `peak_memory: 250MB`, `memory_limit: 256M`, падение внутри `Illuminate/Collections/Collection.php:399`.

То есть лимит 256М уже применён, но запрос всё равно съедает всю память. Падение — в работе с коллекцией в памяти, а не в SQL. Значит, какой-то из наборов данных в `ChatController::buildIndex()` возвращает несопоставимо больше строк, чем ожидалось.

Что именно раздувается — пока не подтверждено данными; в контроллере есть ровно три места без жёсткого потолка:

- `chat_participants` по 50 диалогам — выборка без `limit`;
- `participants->collapse()->pluck('user_id')` и последующая выборка `profiles` — без `limit`;
- `chat_messages` с `limit(300)`, но с полным полем `body` (обрезка делается уже после загрузки в память).

Наиболее вероятная причина при 250 МБ — дубли строк в `chat_participants` (сидеры прогонялись несколько раз), из-за чего одна и та же пара «диалог+пользователь» повторяется тысячи раз, коллекция `groupBy`/`collapse` разрастается, а `profiles` тянется по огромному списку id. Это гипотеза, и первый шаг плана — её проверить, а не чинить вслепую.

## Шаг 1. Диагностика на боевом (без изменений логики)

Artisan-команда `chat:diagnose {user_id}`, которая печатает:

- число диалогов пользователя;
- число строк `chat_participants` по этим диалогам и число дублей `(conversation_id, user_id)`;
- максимальную длину `body` и суммарный объём выбранных 300 сообщений;
- число уникальных `user_id` для выборки профилей;
- пик памяти на каждом шаге.

Запускается на сервере одной строкой, результат сразу называет виновника.

## Шаг 2. Жёсткие потолки в `ChatController::buildIndex()`

Независимо от результата шага 1 — сделать endpoint принципиально не способным съесть память:

- `SELECT DISTINCT` по `chat_participants` + `limit` (например 2000 строк на весь пакет); при превышении — отдавать участников только по direct-чатам, для групповых — только счётчик;
- обрезать `body` на стороне SQL (`LEFT(body, 200)`), а не в PHP;
- `profiles` — `limit` по числу id и выборка только нужных колонок;
- контрольные точки `memory_get_usage()` с логом `chat.index memory` при превышении порога (например 64 МБ), чтобы следующая деградация ловилась до фатала.

## Шаг 3. Чистка данных, если подтвердятся дубли

Миграция, которая удаляет дубли `chat_participants` по `(conversation_id, user_id)` (оставляя минимальный `id`) и добавляет уникальный индекс, чтобы повторный прогон сидеров не воспроизводил проблему.

## Шаг 4. Проверка

- Прогон `chat:diagnose` до и после;
- авторизованный запрос `/api/chats` с боевого токена: ожидание 200 и `peak_memory` в логе профиля < 64 МБ;
- проверка `grep api_fatal` — новых записей нет.

## Технические детали

Файлы: `backend-laravel/app/Http/Controllers/Api/ChatController.php`, новая команда `backend-laravel/app/Console/Commands/ChatDiagnose.php`, новая миграция в `backend-laravel/database/migrations/`. Фронтенд не меняется.
