# Починить деплой бэкенда: продакшен отдаёт старый код

## Что происходит

Workflow «Deploy Backend» доставляет код, но финальная проверка падает: `/api/health` продолжает отвечать `version: cfb6751`, хотя выкатывался `364a951`.

Проверенные факты:

- `/api/health` берёт версию так: сначала файл `VERSION` в корне Laravel, и только если его нет — короткий хэш из `.git/HEAD` (кэш 5 минут).
- Прод отдаёт ровно 7 символов (`cfb6751`), а CI пишет в `VERSION` полный 40-символьный SHA. Значит **веб-процесс файл `VERSION` не видит** и работает по git-фолбэку.
- `cfb6751` («Update plan») — предок `364a951`, то есть на сервере лежит рабочая копия репозитория, обновлённая вручную через `git pull`, а не только доставка из CI.
- В репозитории файла `backend-laravel/VERSION` нет — он создаётся только на сервере шагом деплоя.

То есть либо CI пишет `VERSION` не в тот каталог, который реально обслуживает Apache, либо файл пишется, но недоступен веб-процессу. Какая из двух причин — по логам не определить: сейчас деплой ничего не сообщает о том, какой каталог фактически исполняется в вебе.

## Что сделаем

### 1. Сначала диагностика, потом фикс

Добавим в `/api/health` (в блоке `checks`) безопасные для публикации поля:

- `version_source` — откуда взята версия: `file` (VERSION) или `git` (фолбэк);
- `root_id` — короткий хэш (sha1, 8 символов) от абсолютного пути `base_path()`, без самого пути, чтобы не светить структуру сервера;
- `version_mtime` — время последней записи `VERSION`.

Этого достаточно, чтобы сравнить каталог, куда пишет CI, с каталогом, который исполняет Apache.

### 2. Доказательство «какой каталог обслуживает сайт»

В workflow после rsync добавим шаг: пишем в `public/` уникальный файл-маркер с содержимым текущего SHA, затем скачиваем его по HTTP. Если маркер не отдаётся или отдаёт SPA-заглушку — доставка идёт мимо активного document root, и деплой падает сразу с понятным сообщением, а не через 12 попыток на финальном шаге. Маркер удаляется в конце шага.

Одновременно шаг печатает на сервере: реальный `pwd`, `ls -l VERSION`, `php artisan tinker`-эквивалент через `php -r` с `base_path()`-хэшем (тот же `root_id`), и список всех прочих копий Laravel в домашнем каталоге (`public/index.php` вне активного корня).

### 3. Устранение расхождения

По результату шага 2 возможны два исхода, и оба закрываем в этом же прогоне:

- **Apache смотрит в другой каталог** — правим `BACKEND_ROOT` (переменная `TARGET_DIR`) на реально обслуживаемый корень, а старую копию помечаем как заброшенную: кладём в неё файл `DEPRECATED_ROOT` и валим деплой, если она снова окажется активной.
- **Каталог тот же, но `VERSION` не читается** — пишем файл с явными правами `chmod 644` и проверяем чтение от имени веба тем же маркером; сброс OPcache усиливаем: помимо `touch public/index.php` дописываем `opcache_reset()` через веб-запрос к служебному маршруту, защищённому одноразовым токеном деплоя.

### 4. Убрать ручной `git pull` как источник правды

Раз версия на проде берётся из `.git`, на сервере живёт рабочая копия репозитория. Деплой будет явно сообщать (`::warning::`), если в активном корне есть `.git`, чей HEAD не совпадает с доставленным SHA — чтобы ручные `git pull` больше не создавали иллюзию «выкатилось».

### 5. Проверка после правок

- Прогон workflow до зелёного финального шага (версия из `version_source: file` совпадает с SHA прогона).
- `curl /api/health` — `status: ok`, `fatals_last_hour: 0`, версия равна текущему SHA.
- E2E-набор против прода (api + ui-desktop + ui-mobile) — как в прошлом прогоне, до полного зелёного.

## Технические детали

- `backend-laravel/routes/api.php` — расширение `/api/health` (`version_source`, `root_id`, `version_mtime`); маршрут остаётся публичным, путей сервера в ответе нет.
- `.github/workflows/deploy-backend.yml` — новый шаг «Проверка активного корня» (маркер + HTTP-проверка) сразу после rsync; расширенная диагностика в шаге установки; предупреждение про `.git` HEAD; финальная проверка версии сверяет ещё и `version_source`.
- Ограничение: у меня нет SSH-доступа к серверу — точная причина определяется первым же прогоном workflow с новой диагностикой, поэтому шаг 3 выполняется по факту вывода, без догадок заранее.
