# Устранение фатальной ошибки DbController на боевом сервере

## Подтверждённая причина

- В `origin/main` коммита `5e9afce8` метод уже переименован в `enforceResourceAccess`, и все четыре вызова обновлены.
- На сервере команда запускается из `/home/gro7659365/growth-peak.pro/docs/backend` и загружает корневой `app/Http/Controllers/Api/DbController.php`, где осталась старая версия с `private authorizeResource()`.
- Обычный `git pull` обновляет исходник репозитория во вложенном `backend-laravel/`, но не переносит его содержимое в корень работающего Laravel-приложения.

## План исправления

1. Доставить содержимое `backend-laravel/` из `origin/main` непосредственно в корень боевого Laravel-приложения через существующий workflow `deploy-backend`, который уже использует `rsync` с сохранением `.env`, `vendor` и `storage`.
2. На сервере проверить, что активный файл содержит только `enforceResourceAccess`, а вложенная копия `backend-laravel/` удалена workflow как источник рассинхронизации.
3. Пересобрать autoload, очистить кэши Laravel, применить миграции и обновить PHP opcode cache штатным этапом deploy.
4. Запустить `php artisan test --filter=DbController` уже из активного корня приложения.
5. Проверить два ранее падавших API-запроса (`positions` и `profiles`) с боевой HRD-сессией; результатом должны быть корректные ответы без HTTP 500 и без React error #301.

## Защита от повторения

- Не использовать `git pull` внутри корня развернутого Laravel-приложения: для бэкенда единственным способом доставки оставить `deploy-backend`.
- Проверить в логе выкладки хэш `5e9afce8` или новее и наличие строки удаления вложенной копии, если она была создана ручным `git pull`.

## Критерий готовности

- PHP больше не сообщает конфликт видимости `authorizeResource`.
- Тесты `DbController` проходят.
- Оба боевых `/api/db/*` запроса не возвращают 500.
