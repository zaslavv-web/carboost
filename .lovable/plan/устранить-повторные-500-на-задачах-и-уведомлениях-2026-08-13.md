# Устранить повторные 500 на задачах и уведомлениях

## Что подтверждено

- Бой отвечает актуальным кодом `096f235`, путь чтения — `raw-chunked-v3`, `memory_limit` уже `1024M`.
- `/api/health` прямо сейчас показывает `fatals_last_hour: 3`; последний фатал — именно запрос уведомлений пользователя `1259`.
- Даже публичный health-запрос с одним `select 1` имеет пик Zend-памяти `496 МБ`, при этом реальный PHP-пик всего `0.9 МБ`. Значит повышение с 256 МБ до 1 ГБ не устранило ложное исчерпание памяти на этом Apache/PDO-рантайме.
- До выборки данных защищённый `/api/db/*` делает несколько дополнительных обращений: роли, профиль/компания, проверки middleware и получение схемы таблицы. При таком рантайме их сумма снова достигает лимита.
- Фронт отдельно запрашивает до 300 полных задач и уведомления несколькими query-хуками; уведомления также опрашиваются раз в минуту.

## План исправления

1. **Убрать метаданные БД из каждого запроса**
   - Исключить `SHOW COLUMNS` и `Schema::getColumnListing()` из горячего GET-пути.
   - Использовать проверенный статический список колонок моделей/таблиц для фильтров, сортировки и проекции.

2. **Свести проверки пользователя к одному запросу**
   - Загружать профиль, компанию, верификацию и роли единым запросом-контекстом и переиспользовать результат во всех middleware, политиках и company scope в пределах HTTP-запроса.
   - Не ослаблять проверку компании и ролей; impersonation продолжит использовать effective user.

3. **Сделать лёгкие специализированные чтения**
   - Для employee Today добавить компактное чтение задач с только реально используемыми полями и разумной пагинацией вместо `select=* / limit=300`.
   - Уведомления читать через специализированный endpoint владельца, без передаваемого с клиента `user_id` и без generic CRUD/schema path.
   - Счётчик и список уведомлений объединить в один кэшируемый frontend-query, чтобы не запускать параллельные одинаковые обращения.

4. **Не маскировать фаталы повышением лимита**
   - Сохранить текущий лимит как временную страховку, но добавить в диагностику число SQL-запросов и Zend/реальный пик для каждого из двух endpoint-ов.
   - Возвращать короткий JSON с `error_id` на обычные исключения; shutdown-фаталы продолжать учитывать в health.

5. **Регрессии и проверка боя**
   - Добавить backend-тесты: employee видит только свои задачи/уведомления; manager/HRD и impersonation не получают чужие данные через новые пути.
   - Добавить frontend-тест, что Today не делает старые `select=* limit=300` и дублирующие notification-запросы.
   - После выкладки пройти боевую учётку пользователя `1259`: Today, задачи, уведомления; подтвердить HTTP 200, корректные данные и отсутствие роста `fatals_last_hour`.

## Технический критерий готовности

Оба проблемных сценария выполняются без `Schema/SHOW COLUMNS`, с минимальным числом SQL round-trip, возвращают 200 под реальным сотрудником, а `fatals_last_hour` не увеличивается после повторного прохода.
