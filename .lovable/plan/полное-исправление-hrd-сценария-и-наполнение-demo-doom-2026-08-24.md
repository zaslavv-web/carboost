# Полное исправление HRD-сценария и наполнение demo_doom

## Цель

Закрыть весь список одним релизом: устранить ошибки API и навигации, сделать все карточки и строки открываемыми, наполнить **все** перечисленные модули связанными демо-данными и внедрить администрируемую модель прав для сотрудников, должностей и отделов.

## 1. Сначала устранить системные ошибки

- Исправить `422` при реакции в ленте: проверить фактические ограничения записи, авторизацию и уникальность `(post_id, user_id)`, сделать серверную идемпотентную операцию toggle и синхронизацию счётчика.
- Исправить `404` для `career_step_submission_files`: таблица существует, но сейчас не зарегистрирована в доступном списке generic API; добавить безопасное чтение с проверкой доступа через родительскую заявку и разбить чрезмерно длинный `in`-запрос на порции.
- Исправить `410 Gone` SCORM launch-ticket: проверить создание, срок жизни и повторный запуск тикета, исключить использование уже погашенного тикета и добавить восстановление с получением нового.
- Исправить вступление/выход из сообществ: валидировать пользователя и компанию на сервере, исключить дубликаты членства, корректно обновлять `members_count`.
- Исправить переходы «Дашборд» и клики в People Analytics: только клиентская навигация без полной перезагрузки, сохранение фильтров и рабочий drill-down.
- Для всех мутаций показывать понятную ошибку, а не оставлять неуспешный клик без обратной связи.

- Связать данные между собой и распределить задачи по сотрудникам, отделам, статусам, проектам и спринтам; у каждого демо-сотрудника должен быть непустой «Мой бэклог».
- Убрать дублирующую кнопку `+ Проект`, оставив одну основную жёлтую кнопку создания проекта.
- Добавить строгую проверку сидера: каждый подраздел трекера и каждый сотрудник проверяются после наполнения; при пустом разделе команда завершается ошибкой.

- Для каждой метрики зафиксировать формулу, единицы, фильтры, обработку пустых данных и тестовые контрольные примеры; исправлять подтверждённую первопричину, а не отображаемое следствие.
- Добавить регрессионные unit/API-тесты для критичных формул и drill-down переходов.

## 7. Ролевая модель компании

Существующую матрицу `роль × функционал` заменить/расширить правилами, которые администратор компании назначает субъектам трёх типов:

- конкретный сотрудник;
- должность;
- отдел.

Интерфейс:

- переключатель типа субъекта и выбор конкретного сотрудника/должности/отдела;
- таблица с колонками «Функционал», «Просмотр», «Редактирование», «Скачивание»;
- функционал берётся из единого актуального каталога разделов продукта;
- массовое сохранение, сброс наследуемых правил и явное отображение источника эффективного права.

Технические правила:

- права хранятся с `company_id`, типом и ID субъекта; администрирование — только администратор компании и superadmin;
- итоговое право рассчитывается на сервере с документированным приоритетом: персональное правило → должность → отдел → базовая роль;
- запрет просмотра автоматически запрещает редактирование и скачивание;
- права применяются не только к меню, но и к маршрутам, кнопкам и backend/API операциям;
- запрет нельзя обойти прямым URL или ручным API-запросом;
- журналировать изменения правил.

## 8. Демо-наполнение и контроль полноты

Расширить единый `--only-content`, а не добавлять разрозненные одноразовые сидеры. Наполнение должно быть идемпотентным, связанным с `demo_doom` и включать каждый раздел из этого плана.

После запуска сидер проверяет минимальные количества и связи для каждого модуля: проекты/спринты/бэклоги, лента/сообщества, опросы/тесты, адаптация, performance/360/talent, испытательные сроки/взыскания, HR-документы/КЭДО/политики, отсутствия, магазин, университет и база знаний. Любой пустой или несвязанный обязательный раздел делает запуск неуспешным.

## 9. Проверка «точно всё исправлено»

- Прогнать frontend-тесты, backend-тесты, сборку и проверки миграций.
- Пройти Playwright полный HRD-сценарий и отдельный employee-сценарий на desktop и mobile: открыть каждый перечисленный раздел, выполнить ключевую мутацию и проверить итоговое состояние после обновления страницы.
- Проверить Network: нет `4xx/5xx` для реакций, сообществ, файлов карьерного трека, SCORM и документов.
- Проверить ролевую модель минимум на трёх правилах: сотрудник, должность, отдел; отдельно попытаться обойти запрет прямым API-вызовом.
- Сформировать итоговый чек-лист «пункт → тест → результат». Пункт считается выполненным только при зелёном тесте или подтверждённом E2E.
- Боевой E2E выполнить после появления авторизованной сессии в preview; сейчас среда сообщает `signed_out`, поэтому без повторного входа нельзя честно подтвердить защищённые сценарии на production.

## Подтверждённое текущее состояние

- Матрица прав сейчас хранит правила только по ролям, хотя запрошены сотрудники, должности и отделы.
- Клиентский hook прав сейчас используется изолированно и по умолчанию разрешает доступ при ошибке загрузки; серверное применение матрицы к ресурсам отсутствует.
- `career_step_submission_files` имеет модель и таблицу, но отсутствует в whitelist generic API, что соответствует показанному `404`.
- В тестах popup аудитории уже частично существует, но сохранение выполняется отдельными запросами на каждый checkbox и требует перевода в единый черновик с подтверждением.
- В 360° уже есть массовый выбор сотрудников и фильтр отдела; групп, должностей и системных ролей пока нет.
- HR-документы, КЭДО и типы отсутствий уже имеют часть UI открытия/редактирования; требуется наполнить реальные данные и проверить backend-сценарии.
- Формула Gap действительно вычисляет общую максимальную цель по названию навыка, а не целевой профиль должности конкретного сотрудника.
