# Таймауты у обычных пользователей: разбор лога и план устранения

## Что реально видно в логе

1. `Allowed memory size of 67108864 bytes exhausted ... Connection.php:412`, повторяется пачками для `userId: 1259`. Строка 412 — это выборка (`select`) и гидратация результата. То есть PHP-воркер падает не от «нет соединений», а от **слишком большого результата одного SELECT**. Это отдельная проблема от 1203.
2. `1203 max_user_connections` в стеке `AnalyticsController->ingest` — следствие: воркеры, которые падают по памяти, не отдают соединение штатно, очередь растёт.
3. `DbController query failed ... Unknown column 'body' ... select id,title,body,url,created_at,is_read,type from notifications where user_id = 7` — прод отдаёт **старую сборку фронта**: в репозитории этот запрос уже переписан на `description,notification_type` (`src/pages/employee/EmployeeToday.tsx`). Значит фронт на сервере не пересобран, и каждые 60 секунд каждый пользователь получает 400.

## Что подтверждено в коде

- `DbController::index` ставит лимит **только если** пришёл `limit` или `range`; иначе выполняется `$query->get()` без ограничения (см. блок с `range`/`limit`).
- Экраны обычного сотрудника шлют запросы **без лимита**: `EmployeeToday` (уведомления, компетенции, цели), `useUnreadNotifications` (тянет все непрочитанные строки, чтобы посчитать длину), задачи трекера.
- `CompanyScope` для superadmin выходит сразу и не добавляет фильтр — суперадмин ходит по другим экранам (HRD/админка), где выборки постраничные, поэтому у него всё «работает».

Точную таблицу, на которой рвётся память, лог не называет — фатальная ошибка пишется без маршрута. Поэтому первый шаг плана — инструментирование, а не догадка.

## План

### Шаг 1. Инструментировать (без изменения поведения)

- Зарегистрировать shutdown-хендлер: при фатальной ошибке логировать метод, URI, query string, id пользователя и `memory_get_peak_usage()`.
- В `DbController::index` логировать предупреждение, если результат больше N строк (например 500) или ответ весит больше нескольких МБ: таблица, query string, число строк.
- Выкатить, войти под пострадавшей учёткой, снять точный запрос-виновник.

### Шаг 2. Жёсткие предохранители на бэке

- Ввести дефолтный лимит в `DbController::index` (например 500) когда клиент не передал `limit`/`range`, и потолок 1000, как уже сделано для явного `limit`.
- Возвращать в ответе признак усечения, чтобы фронт мог показать «показаны первые N».
- Отдавать `count` без гидратации моделей (уже есть `getCountForPagination`) — использовать его для счётчиков.

### Шаг 3. Убрать безлимитные запросы на фронте

- `useUnreadNotifications` — считать через `count`/`head`, а не тянуть все строки.
- `EmployeeToday`: лимиты на уведомления (например 20), компетенции, цели; задачи трекера — лимит и фильтр по открытым статусам.
- Пройтись по остальным экранам сотрудника и мобильным лейаутам, добавить лимиты там, где их нет.

### Шаг 4. Переcобрать и выложить фронт

Ошибка `Unknown column 'body'` доказывает, что на проде старый бандл. Прогнать деплой фронта (GitHub Actions `deploy-frontend`) и убедиться, что запрос уведомлений уходит с новыми колонками.

### Шаг 5. Проверка

- Playwright на `growth-peak.pro`: вход под обычным сотрудником и под HRD, прохождение основных экранов, сбор сетевых кодов (не должно быть 400/500/503).
- Повторно снять `storage/logs/laravel.log`: не должно быть ни `memory size exhausted`, ни `Unknown column`.

## Технические детали

- Файлы бэка: `app/Http/Controllers/Api/DbController.php`, `bootstrap/app.php` (регистрация shutdown-хендлера) или `AppServiceProvider`.
- Файлы фронта: `src/hooks/useUnreadNotifications.ts`, `src/pages/employee/EmployeeToday.tsx`, `src/hooks/tracker.ts`, мобильные лейауты.
- Изменения обратно совместимы: контракт `/api/db/{table}` не меняется, добавляется только дефолтный лимит и поле-признак усечения.
