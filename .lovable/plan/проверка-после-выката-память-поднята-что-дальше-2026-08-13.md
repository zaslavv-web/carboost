# Проверка после выката: память поднята, что дальше

## Что показывает боевой сервер сейчас

`/api/health` вернул:

- `memory_limit: 1024M` — новый лимит применился (был 256M)
- `usage_mb: 12`, `peak_mb: 12` — раньше на том же запросе было 64/128 МБ кратными скачками
- `usage_php_mb: 0.8`, `peak_php_mb: 3.1` — реальное потребление приложения меньше 4 МБ
- `db_read_path: raw-chunked-v3` — свежий код бэкенда на месте
- `version: unknown` — файл VERSION при выкате не создался (маркер версии не работает)

То есть накладные расходы аллокатора подтверждены: приложение ест единицы мегабайт, а PHP резервировал десятки. С лимитом 1024M запаса теперь хватает.

## Шаги

1. Повторить в браузере под сотрудником (id 1259) те же экраны, где падали 500: задачи трекера, уведомления, должности, шаблоны треков. Нужен только результат: пропали 500 или нет.
2. Если 500 остались — снять с сервера последние строки лога (`api_fatal`, `db_index_failed`, `db_busy`) и разобрать конкретную причину: это уже будет не память, а SQL или лимит соединений.
3. Починить маркер версии: сейчас `version: unknown`, значит шаг генерации VERSION в деплое не отрабатывает. Без него нельзя быстро отличить «код не выкатился» от «код выкатился, но падает».
4. Добавить в `/api/health` короткую сводку по последним фатальным ошибкам (счётчик за час), чтобы проверять состояние одной командой, а не грепом по логам.

## Технические детали

- Маркер версии: генерация файла `VERSION` в `.github/workflows/deploy-backend.yml` и чтение его в `routes/api.php`; при ручном `git pull` файла нет — сделать фолбэк на хэш последнего коммита (`git rev-parse --short HEAD`) с кэшированием.
- Счётчик фатальных: писать в кэш при срабатывании глобального обработчика ошибок, отдавать `fatals_last_hour` в `/api/health`.
- Лимит 1024M оставляем как есть: реальное потребление 3 МБ, риск утечки минимальный, а понижение обратно вернёт крэши из-за накладных расходов аллокатора.

Нужен только пункт 1 от вас — прогон экранов; дальше действую по результату.
