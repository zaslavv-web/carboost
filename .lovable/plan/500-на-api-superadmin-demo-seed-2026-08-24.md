# 500 на /api/superadmin/demo/seed

## Что известно

Кнопка сидинга демо-данных возвращает 500. Причина сейчас не видна: эндпоинт вызывает artisan-команду `demo:seed` синхронно внутри HTTP-запроса и возвращает JSON только при штатном завершении. Любое исключение внутри команды (или превышение лимита времени/памяти PHP-FPM) вылетает наружу как голый 500 без текста — ни в UI, ни в ответе нет причины. Полный прогон создаёт компанию, оргструктуру, 150 пользователей и контент во всех модулях в одной транзакции, поэтому оба сценария (исключение и обрыв по лимитам) равновероятны, и гадать нельзя — сначала нужно вытащить настоящую ошибку.

## Шаг 1. Сделать ошибку видимой (обязательно, до любых «фиксов»)

- Обернуть `seed`, `reset`, `content`, `careerTracks` в `try/catch (\Throwable)`: возвращать 422 с полями `message`, `exception`, `file:line` и накопленным выводом artisan вместо необработанного 500.
- Писать полный стектрейс в лог с меткой `demo-seed`.
- В UI страницы сидинга показывать текст ошибки из ответа (сейчас показывается только факт неудачи) и оставлять вывод команды на экране.

Результат: следующий запуск сразу называет реальную причину.

## Шаг 2. Снять лимиты, из-за которых обрывается длинный прогон

- В контроллере на время сидинга поднять лимиты: `set_time_limit(0)`, увеличенный `memory_limit`, отключение лимита времени запроса.
- Прогресс-вывод команды собирать построчно, чтобы при обрыве было видно, на каком из 12 шагов упало.

## Шаг 3. Устранить причину, которую покажет шаг 1

Типовые варианты и реакция:
- исключение в конкретном шаге сидера (уникальный индекс, отсутствующая колонка в проде, null в обязательном поле) — точечная правка этого шага плюс идемпотентная проверка перед вставкой;
- обрыв по времени/памяти — разбить прогон на этапы: пользователи отдельно, контент отдельно (`--only-content`), с продолжением по кнопкам, без одной гигантской транзакции;
- отсутствие компании/должностей у выбранной компании — понятное сообщение вместо падения.

## Шаг 4. Проверка на боевом

- Прогон под superadmin на выбранной компании (в т.ч. `demo_doom`): сначала «Дополнить контент», затем полный сидинг.
- Playwright-проверка: страница сидинга без ошибок, счётчики выросли; `/scenarios` под HRD — схема сценария рисуется с шагами и критериями, а не пустым состоянием.

## Технические детали

- `backend-laravel/app/Http/Controllers/Api/Admin/DemoSeedController.php` — try/catch + лимиты + структурированный ответ об ошибке.
- `backend-laravel/app/Console/Commands/SeedDemoCompany.php` — при необходимости разбиение транзакции по шагам и идемпотентные вставки.
- `src/pages/SeedDemoCompany.tsx` — вывод `message`/`output` ошибки в UI.
