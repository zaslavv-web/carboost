# Исправление SSH-доступа для Seed Demo Content

## Причина

Workflow добавляет приватный ключ в `ssh-agent` на шаге `Setup SSH`, но не передаёт `SSH_AUTH_SOCK` и `SSH_AGENT_PID` следующему шагу `Run seeder`. В результате команда сидирования подключается к серверу без ключа и завершается `Permission denied` / exit code 255. Рабочий workflow деплоя уже сохраняет эти переменные через `GITHUB_ENV`.

## Изменения

1. В `Seed Demo Content` сохранить `SSH_AUTH_SOCK` и `SSH_AGENT_PID` в `GITHUB_ENV` сразу после запуска агента — по тому же проверенному шаблону, что используется в `Deploy Backend`.
2. Добавить `ssh-add -l`, чтобы workflow до подключения явно проверял, что ключ загружен; при отсутствии ключа выполнение остановится на диагностическом шаге, а не на удалённой команде.
3. Добавить короткую SSH-проверку перед сидированием, чтобы отдельно различать ошибку авторизации и ошибку запуска Laravel-команды.
4. Проверить синтаксис workflow и затем повторно запустить `Seed Demo Content` с режимом `only-content`.
5. После успешного запуска проверить health-ответ: `shop_products` должен стать больше нуля; если сидер упадёт уже после подключения, разбирать его Laravel-ошибку отдельно.

## Объём

Меняется только workflow ручного сидирования; ключи, серверные данные и логика самого сидера не изменяются.
