# Интеграционное API (v1)

Двусторонний обмен данными с внешними системами: чтение и запись по ресурсам
платформы, получение событий через вебхуки и pull-фид.

Базовый адрес: `https://<стенд>/api/integration/v1`

---

## 1. Ключи и права

Ключ создаётся в разделе **Интеграции → Ключи API**.
Полный токен показывается **один раз**: в базе хранится только SHA-256 и
публичный префикс, поэтому открыть ключ повторно нельзя — только выпустить новый.

### Чьей компании принадлежит ключ

Компания ключа определяет, какие данные он увидит, и после выпуска не меняется —
для другой компании выпускается отдельный ключ.

| Кто выпускает | Компания ключа |
|---|---|
| Администратор компании | своя, подставляется автоматически |
| Суперадмин | выбирается в форме из списка всех компаний |

Суперадмин видит и отзывает ключи всех компаний, в списке у каждого показано
название компании. Администратор компании работает только со своими: указать
чужую компанию в запросе он не может — вернётся `403 forbidden_company`.

```
Authorization: Bearer gp_<prefix>_<secret>
```

Права задаются скоупами вида `<домен>:<действие>`:

| Скоуп | Что даёт |
|---|---|
| `employees:read` | чтение сотрудников |
| `employees:write` | создание и изменение сотрудников |
| `employees:*` | и то, и другое по домену |
| `events:read` | чтение фида событий |
| `*` | всё (для доверенных интеграций) |

Полный перечень скоупов и ресурсов — `GET /meta/resources`.

Дополнительно у ключа можно задать срок действия и белый список IP или
CIDR-подсетей. Отозванный ключ перестаёт работать немедленно.

Данные всегда ограничены компанией ключа: обратиться к записи другой компании
нельзя даже по прямому идентификатору — вернётся `404`.

## 2. Получение данных из платформы

### Список

```
GET /api/integration/v1/employees?limit=100&department=IT
```

```json
{
  "data": [ { "id": "…", "full_name": "Иванов Иван", "department": "IT" } ],
  "page": { "limit": 100, "has_more": true, "next_cursor": "…" }
}
```

Параметры:

- `limit` — до 200, по умолчанию 50;
- `cursor` — значение `page.next_cursor` предыдущей страницы;
- `updated_since` — ISO-дата; отдаёт только изменённое с этого момента
  (инкрементальная синхронизация);
- любое поле из `filters` ресурса; значения через запятую читаются как список:
  `status=approved,pending`.

### Одна запись

```
GET /api/integration/v1/employees/{id}
GET /api/integration/v1/employees/ext:1c_zup:00-0001
```

Запись адресуется как внутренним UUID, так и ключом внешней системы.

## 3. Передача данных в платформу

### Создание и изменение

```
POST   /api/integration/v1/departments      {"name": "Логистика"}
PATCH  /api/integration/v1/departments/{id} {"name": "Логистика и склад"}
DELETE /api/integration/v1/departments/{id}
```

Принимаются только поля из `fields.write` ресурса — всё остальное молча
игнорируется, поэтому лишние поля в теле не приводят к ошибке.

### Идемпотентная загрузка по своему ключу

Основной способ импорта из учётной системы:

```
POST /api/integration/v1/employees/upsert
{
  "external_system": "1c_zup",
  "external_id": "00-0001",
  "data": { "full_name": "Иванов Иван", "department": "IT" }
}
```

Первый вызов создаёт запись (`201`, `"created": true`), повторный — обновляет ту
же самую (`200`, `"created": false`). Соответствие хранится на стороне
платформы, поэтому внешней системе не нужно запоминать наши идентификаторы, а
повторный прогон выгрузки не создаёт дубликатов.

### Защита от повторов при сбоях сети

Если ответ не дошёл и запрос повторяется, передайте заголовок:

```
Idempotency-Key: <уникальная строка запроса>
```

Повтор с тем же ключом вернёт исходный ответ (с заголовком
`Idempotent-Replay: true`) и не создаст вторую запись.

## 4. Получение событий

Любое изменение данных — из интерфейса платформы, фоновых процессов, импорта
из 1С или самого API — попадает в журнал событий. Имена событий:
`{ресурс}.created`, `{ресурс}.updated`, `{ресурс}.deleted`.

### Вебхуки (push)

Подписка создаётся в разделе **Интеграции → Вебхуки**. Тело запроса:

```json
{
  "id": "…", "event": "employees.updated", "resource": "employees",
  "record_id": "…", "cursor": 1024, "occurred_at": "…", "attempt": 1,
  "data": { "…": "…", "changed": ["department"] }
}
```

Заголовки: `X-GrowthPeak-Event`, `X-GrowthPeak-Event-Id`,
`X-GrowthPeak-Delivery` (номер попытки) и подпись

```
X-GrowthPeak-Signature: sha256=<HMAC-SHA256(тело, секрет подписки)>
```

Проверяйте подпись до обработки. Ответ `2xx` считается успехом; иначе доставка
повторяется 6 раз с нарастающей задержкой: 1 мин, 5 мин, 30 мин, 2 ч, 6 ч.
Одно и то же событие может прийти дважды — используйте `id` для дедупликации.

Подписаться можно на конкретное событие (`employees.created`), на весь ресурс
(`employees.*`) или на всё (`*`).

### Фид (pull)

Вебхуки могут не дойти, если приёмник лежал дольше окна ретраев. Фид закрывает
этот случай — событие остаётся в журнале независимо от доставки:

```
GET /api/integration/v1/events?since=1024&resource=employees&limit=100
```

Храните `page.next_cursor` и передавайте его в `since` при следующем опросе.
Курсор монотонно возрастает, поэтому после любого простоя система догоняет
пропущенное без дублей. При пустой выборке курсор возвращается прежним — его
тоже нужно сохранять, иначе следующий опрос перечитает историю заново.

## 5. Самоописание

```
GET /api/integration/v1/meta/resources   — ресурсы, поля, фильтры, скоупы, события
GET /api/integration/v1/openapi.json     — схема OpenAPI 3.0 для генерации клиента
```

В `meta/resources` поле `granted` показывает, что доступно именно вашему ключу.

Оба документа собираются из того же реестра, что и маршруты, поэтому не могут
разойтись с фактическим поведением API.

## 7. Ошибки

| Код | Когда |
|---|---|
| `401` | ключ не передан, не найден, отозван или истёк |
| `403` | ключу не выдан нужный скоуп либо IP вне белого списка |
| `404` | ресурс или запись не найдены (в том числе чужая компания) |
| `405` | операция недоступна для ресурса |
| `422` | в теле нет ни одного поля, доступного для записи |
| `429` | превышен лимит 600 запросов в минуту |

## 8. Как добавить новый ресурс

Ресурсы описаны декларативно в `backend-laravel/app/Integration/ResourceRegistry.php`.
Одна запись открывает наружу REST-маршруты в обе стороны, скоупы, события,
pull-фид и OpenAPI одновременно:

```php
new ResourceDefinition(
    name: 'initiatives',
    model: Initiative::class,
    scope: 'initiatives',
    title: 'Инициативы',
    read:    ['id', 'company_id', 'title', 'status', 'created_at'],
    write:   ['title', 'status'],
    filters: ['status'],
),
```

Наружу отдаются и принимаются только перечисленные поля — новая колонка в
таблице не попадает в API сама по себе.

## 9. Веб-консоли на поддоменах

Две публичные страницы, чтобы интегратор увидел данные и отправил первую запись
без написания кода.

| Поддомен | Страница | Прямой адрес |
|---|---|---|
| `api-out.growth-peak.pro` | **Выдача данных** — список всех методов на чтение, кнопка «Получить данные» на каждом, фид событий | `/integration/outbound` |
| `api-in.growth-peak.pro` | **Приём данных** — подключение внешней системы и форма отправки записи | `/integration/inbound` |

Обе страницы авторизуются тем же API-ключом. Без ключа они не показывают
ничего и не делают ни одного запроса. Ключ хранится в `sessionStorage` текущей
вкладки и уходит только в заголовок `Authorization`.

Перечень методов и поля форм берутся из `GET /meta/resources`, то есть из того
же реестра, что и маршруты API. Новый ресурс появляется на страницах сам.

### Что настроить на хостинге

Код уже готов: страница выбирается по первому лейблу хоста (`api-out` / `api-in`),
всё остальное отдаёт основной домен. Со стороны инфраструктуры нужно два шага.

**1. DNS.** Две записи на тот же адрес, что и основной домен:

```
api-out.growth-peak.pro.  CNAME  growth-peak.pro.
api-in.growth-peak.pro.   CNAME  growth-peak.pro.
```

**2. Веб-сервер.** Поддомены должны смотреть в **тот же докрут**, что и основной
домен. Это не деталь вкуса: в этом докруте лежит `.htaccess`, который роутит
`/api` в `backend/public`, поэтому запросы консолей остаются same-origin и CORS
не участвует. На панели хостинга это «псевдоним домена» (ServerAlias), а не
отдельный сайт.

Если поддомены всё же поднимут отдельными сайтами со своим докрутом, запросы
станут кросс-доменными — тогда нужны записи в `backend-laravel/config/cors.php`
(они уже добавлены) и выпуск сертификатов на оба имени.

**3. Сертификаты.** Оба имени должны попасть в TLS-сертификат — иначе браузер
закроет страницу предупреждением.

Проверка после настройки:

```bash
curl -sI https://api-out.growth-peak.pro/ | head -1     # 200
curl -s  https://api-out.growth-peak.pro/version.json   # тот же коммит, что и на основном домене
```
